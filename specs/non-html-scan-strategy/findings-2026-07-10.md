# Non-HTML URL Handling Strategy (Discussion Draft)

Date: 2026-07-10  
Scope: Strategy discussion only (no code changes)

## 1) What we observed

- URLs discovered from anchors are being queued as scan targets even when they point to non-HTML resources (for example PDF/image links).
- Dashboard and run-level totals are based on queue row counts, so these URLs are currently counted as pages.
- In sitemap or hybrid mode, all sitemap `<loc>` entries are ingested and queued unless excluded by path rules.
- Result: scans remain comprehensive in discovery, but usability suffers because page metrics include non-page resources and failure rates can be inflated.

## 2) Root-cause summary (current pipeline behavior)

Current behavior is URL-centric, not content-type-centric:

1. Discovery extracts hrefs broadly.
2. Filtering primarily checks:
   - same host/domain
   - includePaths / excludePaths path-prefix logic
3. Filtered URLs are inserted into queue.
4. Reporting uses queue counts as page totals.

What is missing today:

- No explicit non-HTML triage step before queueing/auditing.
- No dedicated status class for “intentionally skipped non-HTML resource”.
- No split between discovery inventory metrics and HTML-audit metrics.

## 3) Best-practice target model

Adopt a two-track model:

- **Track A: Discovery inventory (broad)**
  - Discover as much as possible (HTML + documents + media + binaries).
- **Track B: Audit execution (targeted by type)**
  - Audit HTML pages by default.
  - Optionally audit supported document types (for example PDFs) with dedicated checks.
  - Skip media/binary resources from page-audit plugins.

This keeps scans thorough while making results operationally useful.

## 4) Recommended URL triage policy

Classify each discovered URL into one of:

- `html-page`
- `document` (pdf/doc/docx/etc.)
- `media` (png/jpg/gif/webp/mp4/etc.)
- `binary/other`
- `unknown` (needs runtime check)

Triage method (in order):

1. Extension heuristic (fast pre-filter)
2. Response metadata/content type check for ambiguous URLs
3. Fallback defaults if metadata unavailable

## 5) Status and reporting model for usability

Recommended reporting separation:

- **Discovered URLs (all)**
- **Audited HTML pages**
- **Skipped non-HTML resources**
- **Documents (audited vs skipped)**

Recommended queue/result outcome semantics:

- Non-HTML not intended for page audit should be marked as a skip category (for example `skipped_non_html`) rather than failed.
- Failures should represent genuine audit/runtime issues on intended targets, not expected exclusions.

## 6) Suggested defaults

Default behavior for most runs:

- Audit HTML only
- Include documents in inventory
- Do not treat media/binaries as auditable pages
- Optionally allow document auditing via explicit config flag

This default gives cleaner quality signals while preserving crawl completeness.

## 7) Configuration knobs to support strategy

Discussion candidates:

- `auditHtmlOnly: true`
- `auditDocuments: false` (toggle)
- `blockedExtensions: [...]`
- `allowedContentTypes: [...]`
- `documentTypes: ["application/pdf", ...]`
- `countMode: "audited-only" | "all-discovered" | "both"`

## 8) Policy matrix (proposed)

- HTML content type
  - Queue: yes
  - Audit: yes
  - Count in "pages": yes
- PDF/document
  - Queue: yes
  - Audit: optional (document checks)
  - Count in "pages": no (count under documents)
- Image/video/font/static binary
  - Queue: optional for inventory
  - Audit: no
  - Count in "pages": no
- Unknown content type
  - Queue: yes
  - Audit: conditional after type resolution
  - Count in "pages": only if resolved to HTML

## 9) Rollout approach (low risk)

Phase 1 (reporting clarity first):

- Keep current discovery behavior.
- Split dashboard metrics into discovered vs auditable pages.
- Reclassify non-HTML from fail-like noise into explicit skipped categories.

Phase 2 (execution optimization):

- Add triage gate before expensive audit plugins.
- Add optional document audit path.

Phase 3 (policy hardening):

- Domain-specific overrides and per-run policy controls.
- Export-level separation for stakeholder reports.

## 10) Tradeoffs to decide together

1. Should PDFs be audited by default or opt-in only?
2. Should non-HTML resources remain in queue for inventory traceability, or move to a separate discovered_resources table/view?
3. Which denominator should headline KPIs use: all discovered URLs or only auditable HTML pages?
4. Should sitemap ingestion be filtered aggressively at ingest time, or left broad and filtered later by triage?

## 11) Recommendation

For this project’s current UX goals, the strongest default is:

- broad discovery,
- HTML-first auditing,
- explicit skipped_non_html classification,
- KPI denominator based on audited HTML pages,
- optional document audits enabled per run.

This gives the cleanest signal-to-noise ratio while preserving thoroughness and traceability.
